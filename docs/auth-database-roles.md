# Proposed production PostgreSQL roles (review required)

This is a **deployment proposal**, not a migration and not a change to the development database. The current installation still uses `go_web_app` for both migrations and runtime. Before a production cutover, test the exact database copy and application version in staging, back up the database, provision separate credentials, and review the SQL at [`database/scripts/production-roles.sql`](../database/scripts/production-roles.sql). The script intentionally contains no passwords and has not been run on production.

## Roles and rollout

`go_web_app_migrator` owns `framework`, its tables, sequence, and trigger functions, plus `public.schema_migrations`. It executes manual forward migrations. `go_web_app_runtime` has no membership in the owner role and receives only the DML below. The historical `go_web_app` role remains so unchanged migrations 000001–000007 can still be replayed in a fresh installation; the script revokes its framework access after the historical migrations finish. The one-time `bootstrap-admin` command needs an operator-owned database credential with access to `framework.admin_bootstrap`; it must never use the HTTP runtime credential.

For a **new dedicated database**, create the three roles first, provision passwords out of band, grant the migrator database `CONNECT` and `CREATE` on `public`, and run migrations 000001–000007 as migrator. Historical migrations grant to `go_web_app`, so it must exist during migration. Then apply the reviewed role script as a database administrator, set application `DB_USER=go_web_app_runtime`, and restart instances in a planned maintenance window. The script transfers existing object ownership and revokes the old application's grants. It also revokes `PUBLIC` create rights on `public`, a database-wide change that must be reviewed for other tenants. For an **existing database**, inventory all non-framework objects and role dependencies before running the script; it is intentionally limited to known framework objects. Do not run it on the shared development database.

The current `scripts/migrate-framework.sh` accepts `PG*` connection settings. Supply the migrator credential to that script, never the runtime credential. The journal remains `public.schema_migrations`. Future migrations must explicitly grant reviewed runtime DML for each new object and must not rely on old `go_web_app` grants. `ALTER DEFAULT PRIVILEGES` in the script removes future `PUBLIC` function execution for objects created by the migrator; it does not grant blanket table access. Module schemas and `public.schema_migrations_<module>` need their own reviewed ownership and grants. Password rotation and TLS are separate deployment operations; production database TLS must use certificate verification.

## Inventory from migrations 000001–000007 and runtime SQL

| Object | Runtime privileges | Reason |
| --- | --- | --- |
| `framework.sessions`, `framework.oidc_login_flows` | SELECT, INSERT, UPDATE, DELETE | Hashed sessions, one-time OIDC flows, rotation and expiry. |
| `framework.users`, `framework.accounts` | SELECT, INSERT, UPDATE | Verified identity resolution and administrator updates. |
| `framework.roles` | SELECT | Fixed role catalog. |
| `framework.permissions` | SELECT, INSERT | Explicit compiled permission registration. |
| `framework.role_permissions`, `framework.user_roles`, `framework.user_accounts` | SELECT, INSERT, DELETE | Permission/role/account association management. |
| `framework.audit_log` | SELECT, INSERT | Append-only audit writes and history reads. |
| `framework.auth_config_revisions` | SELECT, INSERT | Immutable encrypted revisions and recovery drafts. |
| `framework.auth_config_lifecycle`, `framework.auth_activation_heads` | SELECT, INSERT, UPDATE | Controlled lifecycle and activation head transitions. |
| `framework.auth_activation_history`, `framework.auth_test_evidence`, `framework.auth_recovery_audit` | SELECT, INSERT | Append-only activation, verifier evidence, operator attribution. |
| `framework.admin_bootstrap` | None | Offline one-time operator command only. |
| `public.schema_migrations` | None | Migrator journal. |
| `framework.audit_log_id_seq` | USAGE | Identity generation for audit inserts. |

The runtime receives `USAGE`, not `CREATE`, on `framework`. The script transfers ownership of all framework tables, the audit sequence, and framework trigger functions; indexes and triggers follow their owning tables. The seven framework trigger functions are `preserve_auth_config_revision`, `guard_auth_config_lifecycle`, `guard_auth_activation_target`, `guard_auth_activation_head`, `check_auth_activation_consistency`, `guard_auth_test_evidence`, and `guard_auth_binding`. The triggers guard immutable revisions, lifecycle transitions, activation head/history consistency, test evidence, recovery audit, and session/flow bindings. None of migrations 000001–000007 declares a `SECURITY DEFINER` function; they run as invoker with qualified framework references. Existing `PUBLIC` function execution is revoked. A future `SECURITY DEFINER` function requires a separate threat review, fixed `search_path`, and explicit `EXECUTE` grants.

The 19 user-defined triggers are `auth_config_revision_immutable`, `auth_config_revision_no_truncate`, `auth_config_lifecycle_no_truncate`, `auth_config_lifecycle_guard`, `auth_activation_target_guard`, `auth_activation_head_guard`, `auth_activation_head_consistency`, `auth_activation_history_consistency`, `auth_activation_lifecycle_consistency`, `auth_activation_history_immutable`, `auth_activation_history_no_truncate`, `auth_activation_head_no_truncate`, `auth_test_evidence_guard`, `auth_test_evidence_immutable`, `auth_test_evidence_no_truncate`, `session_binding_immutable`, `flow_binding_immutable`, `auth_recovery_audit_immutable`, and `auth_recovery_audit_no_truncate`. The disposable-cluster test asserts the table, sequence, function, and trigger counts so a future schema change forces a privilege review.

Runtime `UPDATE`, `DELETE`, `TRUNCATE`, and DDL are absent on append-only audit/history/evidence tables. The script does not change trigger or constraint definitions. PostgreSQL object grants cannot prevent a compromised runtime credential from inserting **fabricated** audit rows or manipulating mutable authorization tables within its DML rights; the application's verified principal, advisory lock, and transaction checks remain essential. Separate database roles are defense in depth, not row-level isolation. The offline recovery CLI currently needs writes to activation/lifecycle/history/recovery-audit tables; it may use the runtime DML credential only with its independent cryptographic operator authorization and explicit confirmation. Restrict CLI execution and its key to authorized operators.

## Verification and operational procedures

`go test ./internal/database -run TestProposedProductionRolesInDisposableCluster -count=1 -v` creates a disposable PostgreSQL 14 cluster, applies migrations there, applies the proposed SQL, connects as the runtime role, checks normal user/audit writes, and rejects audit/history modification, migration-journal writes, bootstrap writes, and DDL. It never reads `DB_*` or contacts the development database.

Before a live Auth0 rehearsal, also run the existing targeted regression tests in a disposable cluster: `TestActivationPreparationRequiresExplicitAffinityAndOriginatingInstance`, `TestNormalCallbackReadinessRejectsAnotherInstanceWithoutConsumingFlow`, `TestActivationUnknownCommitOutcomeIsFencedAndNotRetryable`, `TestActivationAmbiguousCommitCanBeAuthoritativelyReconciledWithoutRetry`, `TestSubscribeBeforeReadAndMissedNotificationRecovery`, `TestReconnectBackoffAndTemporaryConnectionFailure`, `TestDiscoveryRetryIsBoundedAndIdempotentOnly`, `TestOfflineRecoveryRejectsUnsafeInputsAndRollsBack`, and `TestActivationPreparationRejectsUnsafeProviders`. They cover cross-instance routing, uncertain commits, listener recovery, IdP 429/503, unavailable database, and callback URI mismatch. For a real reverse proxy, separately inject 502/504 and a dropped response **after** submitting an activation in a non-production rehearsal; inspect authoritative status before any further action. To rehearse recovery during an IdP outage, use a synthetic/staging IdP and confirm preparation refuses recovery before the confirmation prompt. Never use an expired provider as an authentication bypass.

One runtime limitation remains: a request handler that ignores context cancellation indefinitely retains its authenticator lease indefinitely. The dispatcher does not forcibly terminate an in-flight verifier. Audit any newly added blocking handlers; OIDC outbound operations already have bounded HTTP timeouts. A targeted future correction would bind handler-specific external operations to request contexts and enforce server-level read/write/idle timeouts, without closing a legitimate in-flight transport.

See PostgreSQL 14 documentation for [GRANT](https://www.postgresql.org/docs/14/sql-grant.html), [privilege defaults](https://www.postgresql.org/docs/14/ddl-priv.html), and [ALTER DEFAULT PRIVILEGES](https://www.postgresql.org/docs/14/sql-alterdefaultprivileges.html).
